# 哲学学习项目公开开源与活动申请准备设计

## 目标

将当前 v25/90 本地 Git 仓库整理为可信、可复现、适合首次公开发布的开源项目候选，并让仓库清楚呈现其公共价值和维护质量，为后续申请 OpenAI “Codex for Open Source”活动积累真实证据。

本阶段只做本地、可逆准备。不会创建远程仓库、push、改变仓库可见性、发布 Release、访问账户或提交活动申请。

## 项目定位

项目面向中文用户、读屏用户和自主学习者，提供结构化、可交互的哲学学习体验。核心特色为：

- 90 条哲学家学习路线与 181 个知识目录条目；
- 以思想实验、分层讲解和理解检查降低系统学习门槛；
- 引用、定位和内容映射采用结构化数据，便于审计与持续校勘；
- Windows WPF 应用具备键盘和读屏友好设计目标；
- 使用锁定依赖、静态验证、回归测试和 portable 产物门禁维护发布质量；
- AI 讨论是可选能力，基础学习内容不依赖真实凭据或特定服务商。

公开表述必须区分已验证能力和人工未验证边界。不得把静态无障碍检查描述成已完成 Narrator、NVDA、UIA 或物理键盘人工验收。

## 审核信号与仓库证据

公开仓库将围绕活动所重视的信号提供可验证证据：

1. **项目质量**：可复现构建、锁定依赖、测试命令、内容 schema 和引用一致性检查。
2. **维护者职责**：通过真实 Issue 分类、PR 审查、Security 流程、Release notes 和版本维护逐步形成记录。
3. **生态价值**：突出中文哲学教育、无障碍学习和结构化开放教学内容的交叉价值。
4. **真实采用**：公开后收集真实下载、反馈、Issue、讨论和教育/无障碍使用案例；不伪造 Star、用户或提交历史。
5. **Codex 用途**：内容与引用一致性检查、PR 审查、无障碍回归、Issue 分类、跨路线 schema 验证和发布自动化。

## 本地公开准备范围

### 1. 清理公开表面

- 删除或参数化仓库中的本机绝对路径。
- 更新已经与实际 Git 状态不符的本地准备报告，或将纯内部报告移出公开跟踪范围。
- 确保 `bin/`、`obj/`、portable、ZIP、receipt、日志、历史 gate 证据和秘密不进入公开仓库。
- 保留产物 SHA 时仅使用公开 Release 可引用的相对名称，不暴露本机目录。

### 2. 可复现验证

- 默认验证命令必须在干净 clone 中可执行。
- 将依赖仓库外 candidate、gate、staging 的深度审计改为显式可选模式；缺少外部证据时给出清楚说明，而不是使用作者机器的默认路径。
- 保留 `.NET 10`、PowerShell 7、locked restore、Release build 和现有测试流程。
- 为公开前检查增加针对绝对路径、秘密模式、生成物和治理文件的聚焦验证。

### 3. 社区与安全文档

准备以下公开文件：

- `README.md`：价值主张、功能、快速开始、结构、验证、无障碍边界和项目状态；
- `CONTRIBUTING.md`：内容、引用、代码和无障碍贡献流程；
- `SECURITY.md`：私下报告安全问题的原则，不公开真实凭据；
- Issue/PR 模板：缺陷、内容/引用、无障碍反馈和变更核对；
- 首次 Release 草稿：只描述可验证事实，不执行发布。

### 4. 权利与许可证人工门

许可证不在本阶段自动决定或写入。公开前必须：

- 区分代码、原创文档、原创教学内容和第三方材料；
- 审核现代译文、出版社材料、百科内容、图片及长引文的再发布权利；
- 由用户决定代码许可证及文档/内容许可证；
- 根据最终选择建立 `LICENSE`、内容许可边界和 `THIRD-PARTY-NOTICES.md`。

建议候选为代码 MIT、确认原创的文档 CC BY 4.0，但这不是预先决定。

## 数据与隐私边界

- 不提交密码、验证码、恢复代码、API key、真实 credential store 内容或剪贴板内容。
- GitHub profile 只需公开可访问；国家、住址、电话等非申请必需信息不纳入项目文档。
- 申请所需 ChatGPT 关联邮箱和 OpenAI Organization ID 只在最终表单使用，不写入仓库。
- 所有示例配置只引用环境变量名或官方凭据存储方式。

## 验证策略

每项改动采用最小、聚焦验证：

1. 文档链接和必需章节检查；
2. 绝对路径、秘密模式和被禁止构建物扫描；
3. 回归审计无外部证据时的可理解失败/跳过行为；
4. locked restore、应用及测试 Release build；
5. 完整现有测试；
6. `git status` 与跟踪文件边界确认。

只有在共享验证逻辑变化时才运行相关完整回归；不重新运行 portable full gate。

## 顺序与完成定义

实施顺序：公开表面清理 → 可移植验证 → 社区/安全文档 → 权利清单 → 全面本地验证 → 本地提交。

本阶段完成标准：

- 仓库中不存在作者机器绝对路径或内部 release 证据路径；
- 新贡献者可从 README 完成基础构建和测试；
- 社区、安全、无障碍边界和维护流程清楚；
- 许可证与第三方权利仍被明确标记为发布阻断，而不是被忽略；
- Git 工作树干净，并有真实、可解释的本地提交；
- remote、public、push、Release 和活动申请全部保持未执行。

## 后续公开阶段

在用户确认权利和许可证并明确授权后，才可创建公开远程、push 和首个 Release。公开后应优先处理真实用户反馈和 Issue，形成持续维护证据；达到可验证的活跃维护状态后，再准备活动申请的两个 500 字符说明及证据链接。
